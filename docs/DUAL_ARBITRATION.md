# 双人仲裁加分项

## 实现与部署状态

`EscrowBonus.sol` 已同时包含卖家发货与双人仲裁。本次完成代码、页面、时间线和测试，未部署公共测试网，也没有新增真实验收订单、交易哈希或截图。原 `Escrow.sol`、实验三地址和历史订单保留。

构造函数改为两个不同的非零地址：`constructor(address _arbiter, address _arbiter2)`。`arbiter()` 返回第一人，`arbiter2()` 返回第二人，两人身份都从链上读取。地址部署后固定；任一仲裁人可以兼任买家或卖家，但一人不能通过重复操作替代另一个钱包。

## resolve 的规则

任务书要求“两人都调用 resolve 且意见一致才生效”。两个钱包分别发送 `resolve(id, sellerWins)`，不需要线下收集签名。

| 操作/情形 | 状态和资金 |
| --- | --- |
| 第一名仲裁人投票 | 保持 Disputed，资金继续托管 |
| 第二名投相反意见 | 保持 Disputed，资金继续托管 |
| 两名不同仲裁人均投相同意见 | 第二笔交易内自动结算，true 给卖家，false 退买家 |
| 同一个人再次投相同意见 | 回滚，不累计人数 |
| 争议期间修改原意见 | 更新自己的记录；与另一人一致则立即结算 |
| 非仲裁人调用 resolve | 回滚 |
| 已结算后再次 resolve | 回滚，禁止重复转账 |

`resolutionVotes(id, address)` 用 0 表示未投、1 表示退款、2 表示给卖家，避免将 `false` 和未投混为一谈。每次成功提交/修改发出 `ResolutionVoted`；真正结算才发出 `OrderResolved`。不同订单单独记录意见。

修改意见是为避免意见不同后无法继续处理；它不会降低“两名不同钱包、当前意见相同”的门槛。如果两人始终无法一致，资金继续托管，当前实现没有单人强制结算或自动超时仲裁机制。

## 页面与时间线

`EscrowDualArbitrationActions` 显示两人的地址、当前意见、0/2、1/2、2/2 进度和意见分歧说明。双方及旁观者可查看，只有指定仲裁人可投票；已经投过的同一选项禁用，仍可改投另一选项。兼任买家的仲裁人保留付款、确认和争议权限。

提交前重新核对钱包、网络、合约能力、两名仲裁地址、订单状态和自己的最新投票。成功回执后刷新意见与订单，拒签和回滚不会误报成功。第一票提示为“意见已提交”，订单仍显示“争议中”。

时间线展示全部 `ResolutionVoted` 及最终 `OrderResolved`，使用实际事件、交易签名者、区块时间和交易哈希。`lastResolutionVoteBlock` 用于在争议状态下把记录读到最近投票区块，避免停在 OrderDisputed 而漏掉之后的投票，也避免扫描到当前高度的大量空区块。新版仲裁结算时间线若缺少两名不同仲裁人一致的投票记录，会提示记录不完整。

不配置新版地址时继续运行原单人仲裁页面。配置新版地址后同时核验 `supportsShipping()` 和 `supportsDualArbitration()`，两项均为 true 才启用页面交易。
