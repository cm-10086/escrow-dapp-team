## 本地启动

需要 Node.js `>=20.18.3`；项目固定使用 Yarn `3.2.3`。

```sh
corepack enable
yarn install --immutable
yarn start
```

在浏览器访问终端输出的本地地址，订单页面为 `/escrow`，合约调试入口为 `/debug`。开发沿用已有测试网部署，无需先运行 `yarn chain` 或重新部署合约。

常用检查命令：`yarn next:check-types`、`yarn hardhat:check-types`、`yarn lint`。首次编译生成 Hardhat 类型时使用 `yarn hardhat:compile`。现有 CI 已改为编译合约，不会因默认网络为测试网而尝试部署。

## 争议与仲裁的页面集成

`feat/order-list` 已整合蔡的 `584cbcc` 提交。`EscrowOrderRow` 使用事件提供的实际订单号调用 `getOrder`，把订单号及读取到的 `buyer`、`seller`、`status` 传给 `EscrowDisputeActions`。

现有写入 hook 会等待交易成功确认后返回；组件随后触发 `onConfirmed`，订单行调用 `refetch()` 重新读取订单。订单状态和可见按钮随查询结果更新。失败交易不会触发成功刷新。

订单列表通过 `OrderCreated` 事件获取 ID，查询批次为 10 个区块。金额读取订单实际代币的精度与符号。连接买家、卖家和仲裁人钱包时，各订单行根据链上参与人和状态显示对应操作。

本次接入已通过前端 TypeScript、lint 和 4 个权限测试。浏览器在隔离的 RPC 与钱包数据下验证了实际订单号传递、等待回执、争议成功后的状态刷新、仲裁退款后的状态刷新、拒绝签名及失败回执不触发成功刷新，以及卖家权限和移动端布局。公共测试网的三人业务验收仍需使用真实钱包完成。

## 实时新订单的分批读取

POTOS 的事件查询按任务书要求每次最多扫描 10 个区块。原有 hook 的历史读取已分批，但实时读取直接查询“上次位置 + 1”到最新区块，跨度大时可能只收到前 10 个区块的日志，却把读取位置推进到最新区块，导致后续订单遗漏。

实时读取现复用 `blocksBatchSize`，通过 `readEventsInBatches` 顺序补齐整个新增区间。例如上次读到 100，最新为 125，订单页面依次查询 `101–110`、`111–120`、`121–125`。所有批次成功后才合并结果并推进位置；中途失败会保留原位置、显示错误，点击“刷新订单”会同时重试实时读取。没有事件的批次仍继续向后扫描，原有事件去重逻辑继续保留。

首次读取会等待明确的最新区块，避免发送未限定终点的请求；重新读取历史页也不会把已完成的读取位置退回较旧区块。

运行回归测试：`yarn workspace @se-2/nextjs test:events`。8 个用例覆盖 25 个区块分批、区间边界、大整数区块号、空区间、无事件批次、批次失败、不可用结果和非法批次大小。浏览器模拟复现了旧代码漏单，并验证修复后所有新订单可见、失败批次可重试且不会重复显示订单。模拟结果不代替公共测试网验收材料。

## 页面顶部角色提示

当前账户卡片下方显示角色汇总。`getEscrowAccountRoles` 比较钱包地址与链上的 `arbiter`，并从 `OrderCreated` 事件读取各订单的 `buyer`、`seller`；地址比较忽略大小写。同一账户可同时拥有多个角色，例如在不同订单中分别担任买家和卖家，页面会同时显示对应标签并去重。

角色随钱包切换和新增订单重新计算。未连接时显示“未连接”；订单尚未读全或合约信息未就绪时显示读取提示，保留已经确认的角色。只有仲裁人信息、订单数及完整订单列表都读取成功且没有匹配角色时，才显示“旁观者”。查询失败时提供错误提示和刷新重试入口。

顶部汇总身份，每个订单行的按钮仍按该订单的参与人和状态判断，最终交易权限由合约校验。运行角色回归测试：`yarn workspace @se-2/nextjs test:roles`。

9 个角色测试、前端类型检查及 lint 已通过。浏览器模拟验证了未连接与加载状态、买家／卖家／仲裁人／旁观者切换、新订单导致的多角色更新、查询失败后的提示与重试，以及移动端布局。

## 创建、付款与确认收货的页面集成

2026-10-31 将宋的 `438e304` 合并到 `feat/order-list`，按 [交接文档](docs/SONG_HANDOFF.md) 接入 `/escrow`。创建表单从成功回执的 `OrderCreated` 事件提取真实订单号，随后刷新区块高度、事件列表和链上读取。事件 hook 的区块高度查询设置 `cacheTime: 0`，手动刷新时绕过 viem 的高度缓存，避免创建后仍按旧高度查询、等待下一次轮询才出现订单。

每个订单行把完整 `getOrder` 结果及实际 ID 传给 `PayButton`、`ConfirmButton`，保留蔡的争议仲裁组件。付款与确认收到成功回执后只重新读取对应订单。按钮组件保持挂载，以便状态变化后仍能查看交易哈希。付款先检查余额及授权额度，需要授权时等待 `approve` 成功后才发 `deposit`；已有足额授权时直接付款。正式验收需保留授权与付款的两笔交易证据。
